# 🌱 Greenhouse (Tampermonkey userscript)

Unofficial, plugin-based client mod for pvzhtbot.com: core loader,
plugin manager, settings UI, and feature plugins. Built on the confirmed
API behavior documented in `../site-research/docs/api.md`. See the root
README for the ToS / non-affiliation disclaimer.

## Architecture

```
Tampermonkey (userscript-header.js, @run-at document-start)
    -> Core loader (src/core/loader.js)
        -> at document-start (before the site's scripts): register plugins,
           run enabled plugins' earlyInit() hooks
        -> on DOMContentLoaded: UI + every enabled plugin's init()
        -> double-load guard (data-greenhouse-loaded on <html>) - if the
           installed build AND the dev loader both run, only one boots
        -> Site API wrapper (src/api/site-api.js)   -- confirmed endpoints only
        -> Backend client seam (src/api/backend-client.js)  -- unused until needed
        -> Settings store (src/core/storage.js)     -- GM_getValue/GM_setValue,
           incl. per-plugin option values
        -> Page network hooks (src/core/page-network.js) -- lets plugins
           block or answer the PAGE's own fetch/sendBeacon/XHR/<script src>
           (analytics-blocker, api-cache). The mod's own API calls go
           through the same hooked fetch (pageFetch) so they share the cache
        -> Collection watcher (src/core/collection-watcher.js) -- detects any
           user-cards/ write (this mod's or the site's own UI) so plugins
           can live-update without a page reload
        -> Plugin manager (src/core/plugin-manager.js) -- lifecycle, options,
           dependencies, priority order, crash isolation, events
            -> every plugin, auto-discovered at BUILD time:
               `import plugins from 'greenhouse:plugins'` is a virtual module
               generated by build.js from src/plugins/*/index.js and
               src/userplugins/*/index.js (each `export default definePlugin(...)`,
               see src/core/define-plugin.js). No manifest, no loader edits.
    -> UI
        -> Dashboard card (src/ui/dashboard-card.js) -- the "🌱 Greenhouse"
           card in the site's own /dashboard grid; also exports
           addDashboardTile() for plugins
        -> Settings panel (src/ui/settings-panel.js) -- search, toggles,
           auto-rendered per-plugin settings (⚙), crash badges, disclaimer
        -> Shared: modal.js (plugin popups), toast.js (notifications)
    -> Branding: src/core/brand.js (name, disclaimer, THEME colors)
```

### Core plugins (required, always on)
- **crash-handler** (priority 100, starts first) — toasts on any plugin
  crash; auto-disables a plugin after N consecutive startup failures
  (option, default 2); freeze protection via a "starting <id>" marker in
  storage that survives only if the page hung or died mid-start (cleared
  on normal `pagehide`), which counts toward the same threshold. Crash
  log in console: `__greenhouse.crashLog()` / `__greenhouse.clearCrashLog()`.
  Verified live 2026-11-03 with a deliberately-throwing test plugin:
  first load = toast, second load = auto-disabled, third load = stays
  off, other plugins unaffected throughout.
- **analytics-blocker** (priority 90) — blocks Cloudflare + Vercel
  visitor analytics; installed at document-start via `earlyInit`. No
  opt-out options by design. See below.
- **update-checker** — see below.

### archive/
Retired plugins, kept as history. Outside `src/` so never bundled, and
`build.js` fails the build if `src/` imports from it. See `archive/README.md`.

### Plugin folder layout
Each plugin gets its own folder with an `index.js` that does
`export default definePlugin({...})`. The folder name is the plugin id.
`build.js` discovers the folders at build time (folders starting with
`_` or `.` are skipped), so adding a plugin means only adding a folder.

```
src/plugins/                  <- built-ins
├── card-quick-search/
├── crash-handler/            <- core, required
├── deck-buildability/
├── hero-reference/
├── keep-or-scrap-advisor/
└── update-checker/           <- core, required
src/userplugins/              <- your own, same format (README = authoring guide)
└── <your-plugin>/index.js
src/lib/card-text.js          <- shared card-text helpers (emoji cleanup, stats, name matching)
archive/                      <- retired plugins, kept as history only.
├── README.md                 <- how to archive one + index of what's here
├── collection-completion/    <- e.g. retired 2026-11-04 (site built it in)
└── <plugin-id>/              <- NEVER bundled: outside src/, and build.js
    ├── ARCHIVED.md           <- fails the build if src/ imports from it
    └── index.js
```

See `src/userplugins/README.md` for the full plugin-authoring guide
(ctx, options, dependencies, shared helpers).

### Why no floating settings button
An earlier version had a floating ⚙ button as a fallback on pages without
the dashboard grid. Removed by design: settings are now reachable only
from the `/dashboard` "Mod Settings" card, matching the site's own
navigation instead of a persistent overlay on every page.

### Why a backend-client seam with nothing behind it
No feature currently needs server-side state — everything so far is
readable/writable through pvzhtbot.com's own API. `BackendClient` exists
so a future plugin's `context.backend` is always defined (throws a clear
error if called while unconfigured) instead of every plugin having to
special-case "no backend configured". Do not wire up a real backend until
a specific plugin genuinely needs one.

## Live dev loop (auto-rebuild + auto-refresh)

For active development, `dev-loader.user.js` is a tiny Tampermonkey script
that fetches the latest `dist/pvzhtbot-mod.user.js` **fresh on every page
load** via `GM_xmlhttpRequest` (not `@require`, which Tampermonkey caches
and does *not* refetch automatically — a common gotcha) and `eval()`s it.
The loaded bundle itself polls a `/build-id` endpoint and reloads the page
whenever a new build appears.

1. `npm run dev` — builds in watch mode and serves `dist/` on
   `http://127.0.0.1:8787`.
2. Paste `dev-loader.user.js` into Tampermonkey once (Dashboard → Create a
   new script → paste → save). Needs `GM_xmlhttpRequest` grant +
   `@connect 127.0.0.1` — already in the header.
3. Edit `src/`, save. The watcher rebuilds, the open pvzhtbot.com tab
   detects the new build within ~1.5s and reloads itself automatically.

Because `dev-loader.user.js` loads the build asynchronously, `earlyInit`
hooks can land after the site's first requests in dev. They still apply
to everything after that. Only the installed build is guaranteed to
beat the site's bundle. If you pasted the dev loader before 0.3.1,
re-paste it to pick up `@run-at document-start`.

No floating button — only the `/dashboard` "Mod Settings" card opens
settings, matching the site's own navigation instead of an overlay on
every page.

Stop `npm run dev` (or disable `dev-loader.user.js`) when you're done
developing. For normal (non-dev) use, install the real
`dist/pvzhtbot-mod.user.js` directly instead — no dependency on a local
server.

## Building

```
cd userscript
npm install
npm run build
```

Produces `dist/pvzhtbot-mod.user.js` — the Tampermonkey userscript header
(`userscript-header.js`) prepended to an esbuild bundle of everything
under `src/`.

## Installing / testing

1. Build (above).
2. Tampermonkey dashboard → Create a new script (or Utilities → Import
   File) → paste/import `dist/pvzhtbot-mod.user.js` → save.
3. Visit `https://pvzhtbot.com/dashboard`. A "🌱 Greenhouse" card appears
   in the dashboard grid; clicking it opens the settings panel.
4. Console should log `[Greenhouse] ready - N plugin(s) running` with no errors.

## Plugins shipped

### Deck Buildability Helper (`src/plugins/deck-buildability/index.js`)
Adds a "Deck Buildability" card to `/dashboard` (styled like the other
cards). Clicking it opens a centered panel ranking every public community
deck (`GET /decklists/`, 133 observed) by what % of its 12 cards you own
(`GET /user-cards/`), with filter tabs "All / Can build / Close (70%+)"
matching the counts the site's own `/decklists` "Collection" filter shows
natively (confirmed: that filter is entirely client-side, no API call —
see `site-research/docs/decklists.md`) — but centralized on the dashboard,
ranked, and showing exactly which cards are missing per deck instead of
requiring a page visit and per-deck inspection. Read-only, no writes.
Click any deck row to expand it in place: shows the deck's full
description text and its complete 12-card list (owned cards in white,
missing ones in red with `have/need`), click again to collapse. A search
box filters by deck name/hero/archetype/creator/card name (e.g. typing a
card name finds every deck that uses it). Results are paginated 50 at a
time with a "Show N more" button instead of a hard cutoff.

### Update Checker (`src/plugins/update-checker/index.js`)
Required, always-on built-in plugin — shown in settings with a "Required"
badge instead of a toggle (`required: true` on the plugin object; see
`src/core/plugin-manager.js`). Two separate update signals exist:

1. **Tampermonkey's native auto-update** — fully automatic, no user
   action. `build.js` stamps `@version` as `<package.json version>.<UTC
   yyyymmddhhmm>` (e.g. `0.3.0.202611040107`), so every pushed build is
   newer than the last with no manual bump. `@updateURL` points at
   `dist/pvzhtbot-mod.meta.js` (header only, cheap to poll) and
   `@downloadURL` at the full `dist/pvzhtbot-mod.user.js`, both on
   `master` via raw.githubusercontent.com. Tampermonkey checks on its own
   schedule (default: daily; Tampermonkey settings → "Check Interval").
   Bump `package.json` `version` for real releases; the date suffix
   keeps ordering right either way.
2. **This plugin** — the faster nudge. Compares the running build's
   `__PVZHTBOT_MOD_BUILD_ID__` against `dist/build-id.txt` on `master`,
   checked hourly, and shows a banner whose **Update now** button opens
   the `.user.js` URL, which makes Tampermonkey show its install/update
   screen. Dismissal is per-build-id and per-session (`sessionStorage`) —
   dismissing a notice for build X doesn't suppress it once X+1 ships.

**Where it publishes** (GitHub repo, branch, file names, dev port) is
set once in `release.config.js`. `build.js` writes those URLs into the
userscript header and injects them into the bundle as `__GREENHOUSE_URLS__`
(used by update-checker, dev-reload, and the settings panel's Source
link), and `dev-server.js` reads the port from it. Nothing in `src/`
hard-codes a URL. (Exception: `dev-loader.user.js` is a standalone
script you paste into Tampermonkey, so its `127.0.0.1:8787` is typed out
by hand. Update it if you change `DEV_PORT`.)

**Releasing = `npm run build`, commit `dist/`, push to `master`.** Always
release from `npm run build`, never from a `npm run dev` output: dev
builds include the localhost hot-reload poller (`__GREENHOUSE_DEV__`
in `build.js`), release builds compile it out.

### Hero Reference (`src/plugins/hero-reference/index.js`)
Adds a "Hero Reference" card to `/dashboard`. The site's own `/heroinfo`
page is a static image grid with no search and no per-hero detail route
(confirmed via research: the single bulk `GET /heroinfo/` call already
contains every hero's full superpower text — there's nothing more to
fetch per hero). This plugin makes that data actually searchable: type a
hero name, superpower name, or any word from an effect's text, and
matching heroes expand to show their full parsed superpower list.

Superpower parsing follows the recipe in
`site-research/docs/heroes.md`: a hero's `ability` field concatenates all
its superpowers as blocks separated by `\r\n\r\n`, each block's first
line being the superpower name plus Discord-emoji class tags
(`<:ClassName:id>`). Blocks whose first line has no class tag are
token/reminder text (e.g. a conjured minion's stat line), not real
superpowers — flagged as `(token/reminder)` rather than hidden, since the
heuristic was only spot-checked against one hero during research. Emoji
tags are replaced with their readable name (`<:Health:...>` → `Health`)
both in the title and the effect body — the original research only
checked the title line; live testing here found the same raw-tag noise
throughout the body text too and fixed it there as well.

### Analytics Blocker (`src/plugins/analytics-blocker/index.js`)

Blocks Cloudflare Web Analytics (`static.cloudflareinsights.com` beacon,
injected into the HTML by Cloudflare, reporting to `/cdn-cgi/rum`) and
Vercel Web Analytics (`/_vercel/insights/*`, injected by the site's
bundle). See `site-research/docs/privacy.md` for what they collect.
It works in two layers. The scripts are never inserted (dynamic
`appendChild`/`insertBefore`) or are neutralized as the parser adds
them. Any beacon, fetch or XHR to their collection endpoints is also
dropped. Required (always on, no options besides console logging). The
site's own API is untouched.

### Faster Loading — API Cache (`src/plugins/api-cache/index.js`)

Optional, **off by default** (it trades up to `ttlMinutes` of staleness
for speed) — enable it in the Greenhouse panel.

Every API response is `Cache-Control: max-age=0, must-revalidate` with no
validator, so each page view re-downloads cardinfo (~390 KB), decklists
(~140 KB), legacy decklists (~170 KB), public decks (~135 KB), etc.
This plugin answers GETs for a fixed allowlist of **public** paths. Each
was verified byte-identical with and without a login session. Answers
come from Cache Storage (`greenhouse-api-v1`):
- **Fresh** (younger than `ttlMinutes`, default 10): served instantly
  with no request.
- **Stale:** served instantly and refreshed in the background (`instant`
  on). With `instant` off, it waits for the network.
- **Network failure or 5xx:** the cached copy is served.

Concurrent requests for one URL share a download. `user-cards`, profile,
auth, CSRF, decks and all writes are never touched. Turning the plugin
off clears the cache; so does `__greenhouse.clearApiCache()` in the
console. `__greenhouse.apiCacheStats()` shows hits and misses.

Verified 2026-11-03: across repeated SPA navigations, cardinfo and
decklists were each downloaded once while `user-cards` was refetched
every time. After a full reload they were served from Cache Storage.

### Card Quick Search (`src/plugins/card-quick-search/index.js`)
A hotkey (option: Ctrl+K default, Alt+K, or `/`) opens a search over all
of `cardinfo/` from any page: name, aliases, class, tribe, traits, and
ability text, all words must match, ranked by name match first. Each
result shows cost and strength/health, side · class · tribe · rarity ·
traits, cleaned ability text, and owned count from `user-cards/`
(option, refreshed on collection change). ↑↓ move, Enter expands
(full text, flavor, copy name), Esc closes. `cardinfo/` loads once on first open.

Data quirks found while building it (confirmed live 2026-11-03):
- `stats` is positional (cost, strength, health) and the icon in each
  slot varies. The strength slot can be Bullseye/Frenzy/Strikethrough/
  AntiHero/Deadly/DoubleStrike/Overshoot, and the health slot can be
  Armored/Untrickable/Special/healthstrength. `parseStats()` reads by
  position, not by icon name.
- Trait text is stored as icon + label (`<:Bullseye:id>__Bullseye__`),
  so naive emoji replacement gives "BullseyeBullseye". `cleanEmoji()` drops
  an icon that's directly followed by a `__label__`.
- `cardinfo/` `side` is now `"Plants"` / `"Zombie"` (it used to be `"Plant"`).

### Keep or Scrap Advisor (`src/plugins/keep-or-scrap-advisor/index.js`)
Dashboard tile → popup comparing the site's Keep or Scrap guide
(`GET keeporscrap/`) with your collection: Craft picks at 4x, Craft picks
still to get, Keep picks under 4x, then per class each tier's cards as
chips (green 4/4, amber partial, red none; hover shows the guide's note).
Side tabs + "only cards I'm missing" (option for its default).

Caveat: only the guide's written `reasoning` is machine-readable, and
it names the *highlighted* cards per tier (~117 across 10 classes), not
the full tier list (that's only in the image). The UI says so, and never
labels an unmentioned card as Scrap. Section headings parsed: `Craft:`
`Use:` `Hold:` (also `Keep:`) `Usable:` `Niche:`. Other `Word:` lines
(e.g. `Fireweed:`) continue the current section. The guide's names have
typos ("Imitator", "Lima Pleurodon", "Bog of Enlightment",
"Veloci-Radish Packmates"), so cards match through `createCardMatcher()`
(exact → punctuation-insensitive → unique match within edit distance
1–2). All 117 picks resolved correctly.

## Relationship to site-research/

`../site-research/` is the discovery-phase project: captured traffic,
`docs/api.md` (the spec this wrapper is built from), and a standalone
reference copy of the API wrapper
(`../site-research/scripts/site-api-wrapper.js`). `src/api/site-api.js`
here is the userscript-integrated copy — keep them in sync manually if
the API surface changes; `site-research/docs/api.md` is the source of
truth for what's actually confirmed vs. inferred vs. unknown.
